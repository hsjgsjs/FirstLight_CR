# CPU 对弈：强制对手早出牌是否降低水平

入口是 `python -m native_runner.training.v4.evaluate_opening`。它只做推理和完整对局评测，固定使用 CPU，不需要训练服务器或 CUDA。需要提前启动一个已经配置好的原生模拟引擎，并让该引擎保持空闲；不要与采样或训练任务共用同一个端口。引擎及其 VM 的运行要求保持不变。

## 测什么

- **A：参考模型**。建议用准备回退到的学习者 checkpoint，整个实验不更新。
- **B：被测对手**。选训练中使用的固定对手 checkpoint。
- **natural**：双方照常出牌。
- **forced**：仅 B 使用与训练相同的开局超时规则。到达抽样时间仍未提交过非 WAIT 动作时，若它本来选择等待且存在合法动作，就将该次决策改为 ACT；出什么和放哪里仍由 B 决定。若已经自然出牌，不再干预。

默认保留策略采样，包括被迫 ACT 后的动作采样。`--deterministic` 可切换为 argmax，但这时测的是确定性推理，不能直接当作训练采样条件下的结果。界面的手动“强制出牌”入口保持原有行为。

这里测的是固定 B 的行为限制带来的水平变化，不是重新训练后学习者的提升。A 和 B 也可以指定同一份 checkpoint，作为初步自对弈对照；正式判断建议再选不同参考模型复测。

## 公平复测

每个 block 用同一个引擎种子、同一对卡组、相同卡牌顺序和同一超时时间，运行以下四种分配，每种都跑 natural 和 forced，共 **8 局**：

| 分配 | A 所在 owner | A 使用卡组 | B 使用卡组 |
| --- | --- | --- | --- |
| 1 | 0 | 原 deck0 | 原 deck1 |
| 2 | 1 | 原 deck0 | 原 deck1 |
| 3 | 0 | 原 deck1 | 原 deck0 |
| 4 | 1 | 原 deck1 | 原 deck0 |

换卡组时同时移动卡牌顺序、进化/英雄形态可用信息和塔兵。`--match-config` 固定两副卡组；使用 `--deck-pool` 时每个 block 按训练相同的 `sqrt(uses)` 权重抽取两副卡组并打乱顺序，然后冻结到该 block 结束。未指定卡组时沿用 `MatchConfig` 的默认卡组，不能据此判断跨卡组水平。

默认双方统一为 11 级，可选 16 级。执行延迟、连续出牌间隔和可选 gate 温度覆盖都对称应用。未覆盖温度时，每个模型使用各自 checkpoint 保存的温度；同一模型在两种条件下保持一致。

两模型各决策时刻的随机数独立，并在配对条件间复用。B 的额外采样不会改变 A 或后续决策的随机序列。局面因行为不同而分叉是预期现象；复用种子不保证跨平台浮点运算或引擎版本逐位一致。

## 运行

先将以下模型路径和端口替换成自己的实际值。用一组检查运行流程，共 8 局：

```bash
python -m native_runner.training.v4.evaluate_opening \
  --checkpoint-a /path/to/learner-before-early-penalty.pt \
  --checkpoint-b /path/to/fixed-opponent.pt \
  --opening-seconds 8-20 \
  --blocks 1 --seed 1001 \
  --host 127.0.0.1 --port 28000 \
  --cpu-threads 1 \
  --output evaluations/opening-smoke
```

正式评测把 `--blocks` 改为 50 或 100，分别是 400 或 800 局，并用新的输出目录。CPU 资源有限时可以先跑 20 组（160 局），结合区间宽度再决定后续规模。程序顺序复用同一个引擎和两份已加载模型；`--cpu-threads` 控制 PyTorch 算子线程，不是并行对局数。

其他条件通过以下参数设置：

| 参数 | 用途 |
| --- | --- |
| `--opening-seconds 12` | 固定 12 秒的开局超时；也支持 `8-20` 区间 |
| `--match-config /path/to/match.json` | 两副指定卡组及对局规则 |
| `--deck-pool /path/to/pool.json` | 使用训练卡组池；覆盖配置中的卡组 |
| `--battle-level 11` | 统一卡牌和国王塔等级；覆盖 match-config 对应等级字段 |
| `--delay-ticks 21` | 双方相同的动作执行延迟，20 tick = 1 秒 |
| `--min-play-gap-ticks 4-8` | 双方相同的连续动作最小间隔范围 |
| `--gate-temperature 0.2` | 双方使用相同 act/wait 温度 |
| `--max-score-drop 0.05` | 把 B 得分率下降超过 5 个百分点作为明显变弱的阈值 |
| `--plan-only` | 只写计划，不加载 checkpoint、不连接引擎；仍需 Python 项目依赖 |

输出目录必须是新的或空的，防止旧结果混入。`--plan-only` 也会占用输出目录，正式运行请换一个目录。

## 看结果

- `report.md`：中文摘要、B 胜率、B 得分率和配对变化区间。
- `paired_summary.json`：主要统计结果；重点看 `b_score_delta_forced_minus_natural`，负数表示 B 变弱。
- `matches.jsonl`：逐局即时写入，包括完整对局配置、条件、双方首张牌实际落地时间、请求强制和实际覆盖 WAIT 的次数、动作拒绝数。
- `plan.json`：完整赛程和命令行条件。
- `identity.json`：两模型的确切路径、checkpoint ID、SHA-256、保存/实际使用的温度和完整赛程。
- `summary.json`：兼容原评测器的混合总计；判断早出牌影响应使用 `paired_summary.json`，不要使用这个混合值。

得分率为 `(胜 + 0.5 × 平) / 正常结束局数`，与纯胜率分开报告。截断和未结束对局不算平局；一个 block 的 8 局必须全部正常结束，才能进入配对差值统计，避免丢失某一条件后造成偏差。置信区间按整个 block 做 bootstrap，不把共享种子的 8 局当作独立样本。少于 20 个完整 block 时只报告初步结果。

例如设定下降阈值 5 个百分点：差值的 95% 区间全部低于 −5 个百分点，才判为明显变弱；区间全部高于 −5 个百分点，支持下降在阈值内；跨越阈值则尚不能判断。bootstrap 在样本少或结果高度一致时可能过于乐观；需要更多种子和不同参考模型复核。即使通过，也只说明 B 对当前参考模型、卡组分布和限制参数的表现。

先确认 forced 条件确实存在强制覆盖，以及 B 的首张牌落地时间有变化。若大多数局在超时前已自然出牌，此实验对“强制后会不会变弱”的信息很少，应结合实际触发比例解释。

首出时间的两个字段含义不同：`first_play_seconds` 是首次提交牌或技能的决策时间；`first_card_executed_seconds` 是引擎确认首张牌执行的时间，不包含技能，不会把被拒绝动作当成落地。超时限制与训练一样按提交动作计数停止，不会因一次已提交动作后来被拒绝而再次触发；动作拒绝较多时应先检查运行条件。
