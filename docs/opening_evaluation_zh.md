# CPU 对弈：强制对手早出牌是否降低水平

## 一条命令运行

激活项目 Python 环境，在仓库根目录运行：

```bash
bash duel.sh
```

它会读取 `.env` 中已有的 Linux 模拟环境配置，自动选择空闲端口、启动 CPU 模拟引擎、等待就绪，再运行评测。默认使用 **1 个引擎、General 对 General、8–20 秒开局超时、20 组（160 局）**。模拟器不占 GPU。模型前向在能看到 CUDA 时放到 GPU 上，采样仍在 CPU。

首次运行会从 `duel.example.json` 自动生成 **`duel.local.json`**。以后改这个本机文件即可，仍然只运行 `bash duel.sh`；该文件不会提交到 Git，也不会被普通更新覆盖。比如改 `checkpoint_a` / `checkpoint_b` 换模型，改 `blocks` 换组数，改 `opening_seconds` 换截止时间。所有相对数据路径均相对于仓库根目录。

如果只想临时跑一组，使用 `bash duel.sh --blocks 1`；临时参数不改保存的配置。`bash duel.sh --help` 显示其余少量覆盖选项。

**自动续跑**：每次启动会读取 `evaluations/duel-*/` 中同模型、同评测条件的历史记录，从最后一个完整组之后继续，种子自动递增。`--blocks 3` 表示本次新增 3 组；已有 1 组时会接着跑第 2–4 组，不需要手动修改 `seed`。启动时会打印历史完整组数、本次起始组和种子。本次报告仍只统计本次运行。

模型按权重文件内容识别；改变组数、引擎数、CPU 线程数不会重置进度。未完成或截断的组不算完整组，末尾未完成的组下次会重试。历史多引擎运行若中间有缺组、后面已有完整组，默认接在最后完整组之后；可用 `--block-start N` 指定从索引 N 开始补跑（从 0 计数）。需要重复原实验时运行 `bash duel.sh --blocks 1 --block-start 0`。保留历史结果目录才能自动识别进度。旧版日志也可识别模型哈希；旧版使用外部 `match_config` 或 `deck_pool` 文件的记录因缺少当时的文件哈希，不自动复用。

**多开引擎**：运行 `bash duel.sh --engines 4`，或在 `duel.local.json` 中设置 `"engines": 4` 后照常运行 `bash duel.sh`。已有配置文件不含 `engines` 时默认仍是 1。

`engines` 控制同时运行的引擎和评测进程数，`cpu_threads` 控制**每个评测进程**的 PyTorch 线程数，两者不同。例如 20 组、4 个引擎，每个引擎跑 5 个完整组，一共仍然是 160 局。不会把同组的正常/强制、换边/换卡组复测拆到不同引擎。种子、卡组抽样和开局截止时间按全局组号生成，改变引擎数不会改变赛程。

当前每个引擎使用一个独立模拟器，兼容只支持单引擎的 APK。自动启动时，每个引擎最多占用 8 个核（一组 8 局各有一个核），不再把整个模拟钉在一个核上。模拟器默认约 4 GB 内存/引擎，还需给模型推理、系统和临时磁盘留资源。引擎数上限为 64，实际不超过组数，也不超过可用 CPU 数。评测进程的 PyTorch 线程数会提到和每个引擎的核数相同，除非配置里已经写了更大的 `cpu_threads`。

不再需要自己启动第二个终端、指定端口、手动生成结果目录或启动 worker。运行时显示每局进度，结束后在终端显示报告。每次结果自动写入 `evaluations/duel-日期时间-唯一后缀/`：

- `results/report.md`：最终对照报告，其他评测数据也在 `results/`。
- `settings.json`：这一次实际使用的模型和评测参数。
- `engine.log`、`engine/`：引擎启动及运行日志。
- `prepare.log`、`evaluate.log`：参数检查和单引擎评测日志；多引擎日志为 `evaluate-00.log`、`evaluate-01.log` 等。
- `status.json`：退出状态；中断时也保留已完成对局。

`evaluations/duel-latest.txt` 记录最近一次结果目录。程序在前台运行，保持终端开启；按 **Ctrl+C** 会停止评测并清理自己启动的进程和临时模拟器磁盘。正常结束和报错也会自动清理，不会调用训练脚本的全局停止命令。自动启动的对弈任务同一用户一次运行一个。

多引擎时仍看同一个 `results/report.md` 和 `results/paired_summary.json`，其中置信区间基于全部完整配对组重新计算，不平均各引擎的区间。`results/matches.jsonl` 汇总所有引擎记录；各引擎的原始记录、模型 identity 和赛程保留在 `results/shard-00/` 等子目录中。任一评测进程失败会停止其他进程，已完成的记录保留并生成标明未完成的合并报告。

如果已有一个空闲引擎，也可以 `bash duel.sh --existing-engine 127.0.0.1:28000 --engines 1`；这时只运行评测，不启动或关闭外部引擎。已有引擎模式目前只支持一个端点。不要连接正在采样或训练的引擎。

**前提是这台 Linux 主机的模拟环境已经配置好**：可访问的 `/dev/kvm`、准备好的 AVD/资源、APK、probe，以及 `.env` 对应路径。封装负责启动和管理已有环境，不负责首次制作镜像或安装依赖。缺配置、端口冲突、启动失败会显示原因与日志位置。环境准备见[训练指南](training.md)。

## 测什么

- **A：参考模型**。建议用准备回退到的学习者 checkpoint，整个实验不更新。
- **B：被测对手**。选训练中使用的固定对手 checkpoint。
- **natural**：双方照常出牌。
- **forced**：仅 B 使用与训练相同的开局超时规则。到达抽样时间仍未提交过非 WAIT 动作时，若它本来选择等待且存在合法动作，就将该次决策改为 ACT；出什么和放哪里仍由 B 决定。若已经自然出牌，不再干预。

默认保留策略采样，包括被迫 ACT 后的动作采样。`--deterministic` 可切换为 argmax，但这时测的是确定性推理，不能直接当作训练采样条件下的结果。界面的手动“强制出牌”入口保持原有行为。

这里测的是固定 B 的行为限制带来的水平变化，不是重新训练后学习者的提升。A 和 B 也可以指定同一份 checkpoint，作为初步自对弈对照；正式判断建议再选不同参考模型复测。

## 公平复测

每个 block 用同一个引擎种子、同一对卡组、相同卡牌顺序和同一超时时间，运行以下四种分配，每种都跑 natural 和 forced，共 **8 局**：

| 分配 | A 所在 owner | A 使用卡组 | B 使用卡组 |
| --- | --- | --- | --- |
| 1 | 0 | 原 deck0 | 原 deck1 |
| 2 | 1 | 原 deck0 | 原 deck1 |
| 3 | 0 | 原 deck1 | 原 deck0 |
| 4 | 1 | 原 deck1 | 原 deck0 |

换卡组时同时移动卡牌顺序、进化/英雄形态可用信息和塔兵。`--match-config` 固定两副卡组；使用 `--deck-pool` 时每个 block 按训练相同的 `sqrt(uses)` 权重抽取两副卡组并打乱顺序，然后冻结到该 block 结束。未指定卡组时沿用 `MatchConfig` 的默认卡组，不能据此判断跨卡组水平。

默认双方统一为 11 级，可选 16 级。执行延迟、连续出牌间隔和可选 gate 温度覆盖都对称应用。未覆盖温度时，每个模型使用各自 checkpoint 保存的温度；同一模型在两种条件下保持一致。

两模型各决策时刻的随机数独立，并在配对条件间复用。B 的额外采样不会改变 A 或后续决策的随机序列。局面因行为不同而分叉是预期现象；复用种子不保证跨平台浮点运算或引擎版本逐位一致。

## 底层入口（已有空闲引擎时使用）

下面的 `evaluate_opening` 入口仍可直接使用，但它只连接已有引擎，不自动启动模拟器。日常使用上面的 `bash duel.sh` 即可。

先将以下模型路径和端口替换成自己的实际值。用一组检查运行流程，共 8 局：

```bash
python -m native_runner.training.v4.evaluate_opening \
  --checkpoint-a /path/to/learner-before-early-penalty.pt \
  --checkpoint-b /path/to/fixed-opponent.pt \
  --opening-seconds 8-20 \
  --blocks 1 --seed 1001 \
  --host 127.0.0.1 --port 28000 \
  --cpu-threads 1 \
  --output evaluations/opening-smoke
```

正式评测把 `--blocks` 改为 50 或 100，分别是 400 或 800 局，并用新的输出目录。CPU 资源有限时可以先跑 20 组（160 局），结合区间宽度再决定后续规模。每一组的 8 局在同一个引擎的 8 个槽上同时推进，采集用训练的 compact 格式。同一拍所有观测按模型各做一次前向：机器上看得到 CUDA 时这次前向在 GPU 上，采样仍用 CPU 随机数，避免强制出牌打乱配对序列。两份模型仍只加载一次。`--cpu-threads` 控制 CPU 上的 PyTorch 算子线程，不是并行对局数。

其他条件通过以下参数设置：

| 参数 | 用途 |
| --- | --- |
| `--opening-seconds 12` | 固定 12 秒的开局超时；也支持 `8-20` 区间 |
| `--match-config /path/to/match.json` | 两副指定卡组及对局规则 |
| `--deck-pool /path/to/pool.json` | 使用训练卡组池；覆盖配置中的卡组 |
| `--battle-level 11` | 统一卡牌和国王塔等级；覆盖 match-config 对应等级字段 |
| `--delay-ticks 21` | 双方相同的动作执行延迟，20 tick = 1 秒 |
| `--min-play-gap-ticks 4-8` | 双方相同的连续动作最小间隔范围 |
| `--gate-temperature 0.2` | 双方使用相同 act/wait 温度 |
| `--max-score-drop 0.05` | 把 B 得分率下降超过 5 个百分点作为明显变弱的阈值 |
| `--plan-only` | 只写计划，不加载 checkpoint、不连接引擎；仍需 Python 项目依赖 |

输出目录必须是新的或空的，防止旧结果混入。`--plan-only` 也会占用输出目录，正式运行请换一个目录。

## 看结果

- `report.md`：中文摘要、B 胜率、B 得分率和配对变化区间。
- `paired_summary.json`：主要统计结果；重点看 `b_score_delta_forced_minus_natural`，负数表示 B 变弱。
- `matches.jsonl`：逐局即时写入，包括完整对局配置、条件、双方首张牌实际落地时间、请求强制和实际覆盖 WAIT 的次数、动作拒绝数。
- `plan.json`：完整赛程和命令行条件。
- `identity.json`：两模型的确切路径、checkpoint ID、SHA-256、保存/实际使用的温度和完整赛程。
- `summary.json`：兼容原评测器的混合总计；判断早出牌影响应使用 `paired_summary.json`，不要使用这个混合值。

得分率为 `(胜 + 0.5 × 平) / 正常结束局数`，与纯胜率分开报告。截断和未结束对局不算平局；一个 block 的 8 局必须全部正常结束，才能进入配对差值统计，避免丢失某一条件后造成偏差。置信区间按整个 block 做 bootstrap，不把共享种子的 8 局当作独立样本。少于 20 个完整 block 时只报告初步结果。

例如设定下降阈值 5 个百分点：差值的 95% 区间全部低于 −5 个百分点，才判为明显变弱；区间全部高于 −5 个百分点，支持下降在阈值内；跨越阈值则尚不能判断。bootstrap 在样本少或结果高度一致时可能过于乐观；需要更多种子和不同参考模型复核。即使通过，也只说明 B 对当前参考模型、卡组分布和限制参数的表现。

先确认 forced 条件确实存在强制覆盖，以及 B 的首张牌落地时间有变化。若大多数局在超时前已自然出牌，此实验对“强制后会不会变弱”的信息很少，应结合实际触发比例解释。

首出时间的两个字段含义不同：`first_play_seconds` 是首次提交牌或技能的决策时间；`first_card_executed_seconds` 是引擎确认首张牌执行的时间，不包含技能，不会把被拒绝动作当成落地。超时限制与训练一样按提交动作计数停止，不会因一次已提交动作后来被拒绝而再次触发；动作拒绝较多时应先检查运行条件。
