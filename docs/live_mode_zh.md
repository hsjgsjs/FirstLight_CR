# 实战模式：让 FirstLight 在 MuMu 上和你打

[首页](../README.zh-CN.md)

目标：你在手机上用自己的 Null's 账号操作，MuMu 上的另一个账号由 FirstLight 模型控制，两边打友谊战。

做法：probe 的实战模式挂到游戏自己运行的对局上，在游戏线程里采集 FirstLight 的完整观测；BattleEnvV1 和 V4 策略按 FirstLight 自己人机对战（`offline_agent`）的方式做决策；出牌变成 adb 在 MuMu 屏幕上的点击。挂接方式、控制器偏移、评分弹窗修复、点击时序规则都来自 [Jason-XII/clash-royale-battle-engine](https://github.com/Jason-XII/clash-royale-battle-engine)，它和 FirstLight 用的是同一个 libg 构建。

**只用于你自己的账号。**

## 准备（每次更新代码后）

1. 拉取最新代码，用 `build_offline_engine.ps1` 和 `install_offline_engine.ps1` 重新构建并安装 APK（probe 有改动）。
2. MuMu 渲染模式用 Vulkan。
3. 让游戏联网启动并转发控制端口：
   ```powershell
   .\.venv\Scripts\python.exe -m native_runner.live_diagnose start
   ```
4. 用完后恢复断网：`.\.venv\Scripts\python.exe -m native_runner.live_diagnose offline`（下次运行 `start_offline.ps1` 时也会自动恢复）。

## 第 1 步：校准点击位置

点击坐标取决于 MuMu 的分辨率。**1440×2560 已经按截图测好，写在代码里**（`MEASURED_LAYOUTS`）：

- 格子：左 101、上 196、右 1330、下 1967。每格 68.3×55.35 像素，是按草地棋盘格的格线拟合出来的，残差 1–2 像素。用河道核对过：第 15、16 行在 y 1026–1137。
- 手牌中心：x 446 / 720 / 990 / 1260，y 2270。
- 英雄技能按钮：(1295, 1940)。

`runs\live\layout.json` 如果还没校准，会被自动换成这份测好的布局。你自己手动校准过（`"calibrated": true`）的文件不会被覆盖。

其他分辨率，或者想重新检查时：

1. 手机上向 MuMu 账号发起友谊战，进入对局后运行：
   ```powershell
   .\.venv\Scripts\python.exe -m native_runner.live_play shot
   ```
   第一次运行时，如果还不知道 MuMu 账号是哪一方，加上 `--owner` 或 `--account-id`。
2. 它会往 `runs\live\` 里保存三个文件：
   - `shot-<时间>.png`：原始截图；
   - `shot-<时间>-layout.png`：叠加了布局的截图；
   - `shot-<时间>.json.gz`：同一时刻的实战采集数据。

   叠加图里各种标记的含义：
   - 青色网格：18×32 的格子；
   - 橙色圆圈：按布局算出的塔的位置，旁边标着读到的血量；
   - 蓝色、红色小圈：我方、对方的单位；
   - 紫色圆圈：4 个手牌位置；
   - 黄色圆圈：英雄技能按钮。
3. **左右方向**：每个橙色圈旁边的血量，要和画面上同一座塔的血条数字一致。如果左右两座塔的血量互换了，说明布局把场地左右镜像了，这时千万不要真出牌，把三个文件发给我。所以检查时最好挑两边塔血量不一样的时候截图。
4. 网格、手牌、按钮对不上时，也把这三个文件发给我。

## 第 2 步：让模型出牌

```powershell
.\.venv\Scripts\python.exe -m native_runner.live_play run --account-id <MuMu 账号的 accountId>
```

- 运行后它会一直等待。你每发起一局友谊战，它就挂上去打这一局，打完继续等下一局。按 Ctrl+C 停止。
- `--account-id` 只需要第一次给，之后记在 `runs\live\seat.json` 里。使用本地采集中的账号 ID 确认 MuMu 账号所在座位，账号 ID 和座位文件均不要提交或公开分享。
- `--dry-run`：只做决策、写日志，不点击。适合先看模型会怎么出牌。
- 出牌默认按模型给出的概率**采样**，和 FirstLight 自带的人机对战一样。`--deterministic` 改为每次都选概率最高的动作，但模型每 0.25 秒决策一次，单看每一次，“等待”几乎总是概率最高的，所以这样模型几乎不出牌。
- `--games N`：打 N 局后退出；与 `--auto-queue` 配合时，最后一局结束后不会再点击下一局匹配。等待匹配期间不定时重点击；采集/控制错误会保留档案并停止，绝不会触发返回大厅或重新排队。发现已有对局时先验证完整观测再接管，不发送大厅点击；`attached` 并不保证是真实对局，大厅动画也可能触发。此时自动模式明确报错停止，应先核对画面，在大厅单次点击对战，再用不带 `--auto-queue` 的命令接管。等待有效观测最多 90 秒，超时停止且不重复点击。
- 终端会报告点击后的手牌轮换，并即时警告手牌长时间未变化的疑似丢失操作。手牌变化只是辅助证据，录制中的实际 native 部署事件才用于确认出牌。每局总结的 `tap_counts` 区分已发送、手牌变化、疑似丢失和跳过，原有 `taps` 仍是模型选择的非等待动作数量。
- `--device cpu|cuda`：默认有显卡就用 cuda。
- 每局的日志写在 `runs\live\<时间>.jsonl`，内容包括每次决策（推理耗时 `inference_ms`、游戏线程上的采集耗时 `capture_us`）、每次点击、被跳过的点击和原因、疑似丢失的点击。打完把日志发给我。
- `--min-play-gap-ticks 8-12`：连续出牌/技能至少间隔随机 0.4–0.6 秒，默认开启，按游戏 tick 等待。
- `--record`：额外保存本局全部实际采集的原始观测、策略局面、动作及结果，输局和错误也保留。录制目录及校准、完整性检查命令见[专项训练与实战录制](targeted_training_live_recording_zh.md)。`--record-screenshots` 可选保存开局/结束的调试截图，会增加 ADB 耗时。

### 点击规则（来自 Jason 在 MuMu 上的实测）

- tick 94 以前点击无效，所以这之前的出牌一律跳过。
- 出牌是两次点击：先点手牌，再点格子。在同一条持久 ADB shell 命令中执行两个 `input tap`，不额外添加按住或等待时间；命令结束只表示输入已发送，实际出牌以原生 `card_play` 回执为准。牌在点击后约 21～25 tick 生效，这时下一张牌才发到这个槽位。在这之前，这个槽位在屏幕上是空的。
- 新发的牌要过约 100ms（2 tick）才接受点击。
- 所以对同一个槽位：上一张还没生效、或者新牌刚发下来，这时的点击都会被跳过，并记进日志。BattleEnvV1 自己也会把在途的牌从可选项里去掉，并预留它的圣水。

## probe 命令

| 命令 | 作用 |
| --- | --- |
| `live on` / `live off` / `live status` | 开关实战模式；`status` 返回是否已挂上对局、tick、采集次数、上次采集在游戏线程上花了多少微秒（`captureMicros`） |
| `live observe-atomic [c p v r]` | 在游戏线程上、对局刚更新完的那一刻采集一次完整观测。可选的 4 个数分别是战斗事件、相位、可见性、剩余时间这四个事件环的游标，带上后只发送游标之后的事件 |

实战模式开启时，普通的 `observe`、`observe-rich`、`observe-atomic` 会被拒绝，因为在控制线程上读一个正在运行的对局，读到的状态前后不一致。

## 诊断记录

### 第 1 轮（2026-10-12）

- 5 个样本全部通过 FirstLight 的 atomic/rich 校验，General 模型能在实战数据上正常决策。
- 发现并修复：挂接时只登记了战斗事件，相位、移动、角色状态、塔兵四类遥测一直报“不完整”。

### 第 2 轮（2026-10-12）

- 5 个样本全部通过校验。8 类遥测全部 `complete=true`，上一轮的修复生效了。
- 发现：probe 每次都会把事件环里保留的全部历史发出来。开局 15 秒后一次采集就从 200KB 涨到 1.7MB，游戏线程上的耗时从 62ms 涨到 172ms。对局越往后越大，最多到几 MB，会让游戏卡顿。
- 修复：事件环改为只发增量。BattleEnvV1 本来就按序号逐条消费事件，并记着每个环消费到了哪一条，所以每次采集都带上它的游标，probe 只发游标之后的事件。两轮样本、两个座位共 4 组离线回放，增量模式和整环模式给出的决策完全一致。
- 离线回放把录好的样本当成一局实战来放，走的是和 `live_play run` 相同的代码（`env.step`、出牌回执校验、在途核对），只是不点击：
  ```powershell
  .\.venv\Scripts\python.exe -m native_runner.live_diagnose replay runs\live-diagnose\<时间> --owner 1
  ```
  第 2 轮 owner 1：tick 666 下骑士到 [3,18]，tick 727 下弓箭手到 [0,25]，tick 914 下一张费用为 1 的牌到 [8,31]。录像里这些牌当然没有真的下出去，所以日志里会记为疑似丢失。

### 离线复现启动错误

用失败录制中的原始 capture 初始化完整实战环境并让原模型做一次决策，全程不连接模拟器、不发送点击：

```powershell
.\.venv\Scripts\python.exe -m native_runner.live_preflight "runs/live/recordings/match-实际目录/captures/00000003.json.gz" --checkpoint "你的当前检查点.pt" --account-id <本地采集中的账号ID>
```

看到 `PREFLIGHT_OK` 才说明该采集帧能够通过环境校验和模型推理。实战牌组配置会读取原始 `towerTroopRuntime.kind` 中的皇家厨师、飞刀塔兵类型；之前统一默认公主塔，会使对手使用皇家厨师的对局在模型出牌前报错。此修复保留所有严格的塔兵运行态校验，不修改 probe 或忽略错误。不带特殊运行态的其他塔兵目前仍沿用原公主塔默认值，尚不能据此宣称支持了所有塔兵识别。

### 已知限制

- 实战采集里没有牌组的进化/英雄槽位标记。现在这样确定每张牌的形态：
  - 牌组和手牌的 `cardParameter` 里带着当前形态码。英雄牌从开局就是英雄形态（2），读到就标为英雄。
  - 读不到形态的，可进化的牌只有前两个槽位算进化槽。
  - 对局中如果 BattleEnvV1 仍然报“形态未被牌组契约开放”（比如进化牌充能完成后才显示进化形态），就从报错里取出是哪张牌、什么形态，补进契约，重建这一局的环境后继续打。每局最多重建 4 次，日志里记为 `contract_rebuild`。重建后模型的记忆会从头开始。
- 英雄技能按钮的位置还没校准。按钮只在英雄在场时出现，所以要在英雄在场时截图（`shot`）。
- 新 PPO 训练默认带 `--execution-delay-ticks 18-24`，以覆盖约一秒的点击到执行延迟；旧模型和原始人类缓存不保证具备同样的时序。实战还叠加采集、推理和 ADB 耗时，应通过录制中的 native 部署事件测量，不能只看预估回执。
