# 固定条件五模型循环赛

在 Mac 的仓库根目录、已激活 Python 环境中，连接已有空闲引擎运行：

```bash
bash round_robin.sh --existing-engine 127.0.0.1:28000
```

默认只有一个引擎、16 槽、10 个 PyTorch 推理线程。顺序运行全部十个模型对，每对一次加载双方模型，跑完全部分配的组号，再换下一对。外部引擎贯穿全部模型对；程序不启动、不停止或重装外部模拟器。

默认模型：

| 名字 | 文件 |
| --- | --- |
| General 460 | `checkpoints/General/checkpoint-step-00000460.pt` |
| Update 48 | `checkpoints/my/update-00000048.pt` |
| PPO 104 | `checkpoints/my/update-00000104.pt` |
| PPO 1208 | `checkpoints/my/update-00001208.pt` |
| BC 200 | `checkpoints/my/update-00000200.pt` |

卡组池读取 `.env` 的 `CR_PPO_DECK_POOL`，未设置时使用 `runs/deck-pool.json`。也可直接加 `--deck-pool /实际路径/pool.json`。缺少模型或池文件会停止，不使用固定标准卡组补位。

需要调整时复制 `round_robin.example.json` 为 `round_robin.local.json`，编辑其中的路径或设置。该本机配置不会提交 Git。支持 `--config` 选择另一份配置。

`round_robin.local.json` 必须放在仓库根目录（与 `round_robin.sh` 同级），并且每台运行的机器各自需要一份。找不到时程序会使用 `round_robin.example.json` 的默认设置（五模型十对、确定性出牌）。启动后第一行会显示实际读取的配置文件，或提示未找到；第二行列出模型、是否采样和出牌温度，不符合时按 Ctrl+C 停止。

示例对局参数：16 级、每次决策随机抽取 18–24 tick 执行延迟、连续动作间隔 6–10 tick（2026-10-16 起的统一默认；首轮结果使用 4–8）、确定性出牌。它们不代表已实际读取服务器 `trainer-options.txt`；正式运行前请对照服务器保存的阶段参数核实。采样模式必须显式提供对所有模型一致的 `gate_temperature`。设备默认 `cpu`。

## 规模与分工

默认 `--blocks 0-99`，上下界都包含。每个组号在每对模型中各跑四局正常开局：双方交换位置 × 交换完整卡组。每对 400 局，五模型十对共 4000 局。16 槽同时推进四个完整组。

只检查完整流程可用 `--blocks 0-3`，十对共 160 局；该结果仅适合检查流程。

静态分布运行：

```bash
# 已准备 Linux KVM 引擎环境的服务器，启动一次引擎跑完所有模型对
bash round_robin.sh --blocks 0-79

# Mac：使用通过 ADB 转发的外部引擎
bash round_robin.sh --existing-engine 127.0.0.1:28000 --blocks 80-99
```

服务器支持 `--engines N`，按完整组静态划分；Mac 以上命令始终只有一个引擎。两台机器需使用相同代码、模型、卡组池、设备类型和对局设置。CPU 线程数、文件绝对路径、端口及负责的组号不属于研究身份。

## 续跑与合并

每次创建 `evaluations/rr-*/`，逐局写入日志。重复同一命令会扫描同身份历史，按“模型对＋全局组号”跳过已完整正常结束的四局组。不完整组重新跑；截断不计平局。不要删除历史目录。

复制 Mac 的整个 `rr-*` 原始目录到服务器，例如 `mac-results/`，再运行：

```bash
python -m native_runner.round_robin report evaluations/rr-*/ mac-results/rr-*/
```

合并只读原始数据，不需要加载模型或连接引擎。同一完整组的重复副本只计一次，同一对局出现冲突结果则报错。模型 SHA-256、卡组池 SHA-256、对局设置、代码身份或引擎/资源身份不同会拒绝合并。

每次运行自动生成自己的 `report/report.md` 和 `report/summary.json`，包含本机同身份完整历史。显式合并默认输出到 `evaluations/round-robin-report/`。

## 统计与数据

报告提供每对胜负平、得分率及完整组 bootstrap 的 95% 区间。等级分采用 Bradley–Terry 拟合、Elo 尺度，General 460 固定为 0；不是训练过程中已有的等级分。拟合每对每方向加入 0.5 个伪胜，使全胜/全负仍得到有限值，并在报告中明确标注。

等级分只使用所有模型对共同完整的组号，每次 bootstrap 同时重采样这些组号，再重新拟合，保留共享卡组/种子的相关性。只有部分模型对完成时先报告每对得分率。少于两组时不计算区间；样本极少或结果完全一致时区间可能过窄。

运行目录包含：

- `study.json`：全部模型 SHA-256、对局设置、池和代码身份。
- `settings.json`：本机实际使用的模型路径、池路径、设备和线程数。
- `shard-*/engine.json`：引擎、probe 和内容资源的实际身份。
- `shard-*/pair-*/plan.json`、`identity.json`、`matches.jsonl`：赛程、实际加载模型身份、逐局原始结果。
- `shard-*/pair-*/timing.json`：引擎重置、张量化、模型前向、动作选择和引擎步进墙钟耗时。步进墙钟包含传输和观测处理，不等同于纯 native CPU 时间。
- `report/matches.jsonl`：去重后的完整组对局，带模型名字，方便后续分析。

`duel.sh` 保持原用途，用于正常/强制开局对照。

## 首轮结果（2026-10-15 至 10-16）

用户提供了两份各 21 个完整组的报告（每对 84 局，确定性出牌，示例配置中的 16 级、18–24 tick 延迟、4–8 tick 间隔）。用户确认两份使用的组号**不重叠**，因此两份抽到的卡组组合与种子不同，可直接合并；两份差异属于不同卡组样本带来的波动，不涉及逐局复现性问题。

| 模型 | 第一份 | 第二份 | 两份按局数合并（无区间） |
| --- | ---: | ---: | ---: |
| General 460 | 0 | 0 | 0 |
| Update 48 | −37.0 | +32.8 | −2 |
| BC 200 | −33.7 | +15.6 | −9 |
| PPO 1208 | −65.0 | +23.0 | −21 |
| PPO 104 | −32.9 | −14.0 | −24 |

合并列为按两份胜负平合计重新拟合的 Bradley–Terry 点估计，仅供参考；正式结论应使用 `round_robin report` 合并原始目录得到的区间。

**解读：**

- 十对得分率的两份差值中，最大一对（Update 48 对 PPO 104）约为 2.4 倍标准误，其余均在 1.7 倍以内；十对差值平方和约 15.2，低于 10 自由度 5% 临界值 18.3。即使按各局独立的偏乐观假设，两份结果也与随机波动一致；同组四局共享种子与卡组，实际波动更大。
- 第一份中 PPO 1208 的区间未包含 0，但第二份没有复现。十对同时比较、每对仅 21 组时，单份结果出现个别“显著”是常见现象，只看合并后的累计结果。
- 合并后各模型相对 General 460 都在约 ±25 Elo 内，各对得分率在 43%–55%。在这组条件下没有测出比 General 460 更强的后续模型。
- 今后若两次运行使用相同组号，确定性出牌下结果应几乎逐局一致；胜者一致率明显低于 100% 说明对局不可复现（如设备或推理线程数造成的浮点差异），需先排查。此时 `report` 合并也会因同一组结果冲突而报错。
- 平局只出现在涉及 PPO 104 与 BC 200 的对局中，需检查这些局的首次出牌时间与结束 tick，排除双方长时间不出牌。
- 本条件下的等级分只适用于确定性出牌与上述时序；General 460 的训练时序尚未核对。采样条件应另行评测，不与确定性结果合并；用户提供的实战出牌温度为 0.2，采样评测在配置中设 `"sample": true, "gate_temperature": 0.2`，所有模型使用同一温度。

**样本量：** 分辨 20–30 Elo（约 3–4 个百分点）的差距约需每对 1000 局量级。十对全跑代价过高，后续优先定向对比（例如新模型对 General 460、新模型对迁移前同源模型），从已有组号继续追加，直到区间能排除设定差距。

## 采样条件首份结果（2026-10-16，温度 0.2）

Mac 单引擎，三个模型（General 460、PPO 1208、BC 200），21 个完整组（每对 84 局），采样出牌、所有模型 gate 温度 0.2，16 级、18–24 tick 延迟、6–10 tick 间隔（以 `study.json` 为准）。不与上节确定性结果合并。

| A | B | A 胜 / B 胜 / 平 | A 得分率 | 95% 区间 |
| --- | --- | --- | ---: | --- |
| General 460 | PPO 1208 | 42 / 42 / 0 | 50.0% | [40.5%, 58.3%] |
| General 460 | BC 200 | 43 / 41 / 0 | 51.2% | [41.7%, 60.7%] |
| PPO 1208 | BC 200 | 49 / 35 / 0 | 58.3% | [52.4%, 64.3%] |

等级分：PPO 1208 +16.4 [−27.7, 63.6]，General 460 0，BC 200 −24.6 [−83.1, 27.3]。

**解读：**

- 采样条件下两个模型对 General 460 仍约 50%，与确定性条件的平台期结论一致。
- PPO 1208 对 BC 200 的区间未包含 50%，提示 BC 200（1208 之后的 200 次人类 BC 阶段）在直接对局中可能略弱，即拟人性改造可能有少量实力代价。仅 21 组、三对同时比较，属初步信号，需加组复核。
- 因此近期指令对照实验（两边都从 BC 200 出发）的评测名单应同时包含 PPO 1208，判断训练是否回到并超过 1208，而不只是超过起点。
